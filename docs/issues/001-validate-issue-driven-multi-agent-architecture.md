## 背景

公司项目 Alvax 当前面向美国 2–10 人的 B2B 专业服务企业，拟通过“服务 + 软件”的方式完成网站分析、修改、审核、发布和效果基线记录。市场调研显示，客户真正缺少的不是另一份 SEO 报告，而是可信、可核对、可批准、可追溯的实际变更。

Aegis 不是 Alvax 的替代项目，也不是另一个准备商业化的网安产品。它是 Alvax 的前置技术验证场，目的有两个：

1. 验证基于 Issues 的多 Agent 协同架构是否可行，提前发现任务拆解、依赖调度、上下文传递、验收返工、人工干预和成本控制方面的问题。
2. 使用熟悉的红队与安全研发场景进行高强度实验，判断 Agent 的分工、证据记录、交接和复盘方式是否符合真实红队工作习惯。

网安场景在这里是实验载荷，不是产品方向。它具有目标开放、过程不确定、强依赖证据、需要分工协作和必须保留审计记录等特点，适合尽早暴露多 Agent 系统的问题。

## 要回答的问题

1. 一个目标能否稳定拆成层级化 Issues，并通过依赖关系安全地并行执行？
2. Agent 之间能否传递足够的上下文、证据和接口约定，而不依赖操作者反复转述？
3. 失败、超时、返工、取消、恢复和人工接管是否都有明确状态与记录？
4. 最终验收能否基于原始证据，而不是仅相信执行 Agent 的总结？
5. 系统的 token、时间、人工操作和调度开销是否低于多 Agent 带来的收益？
6. 工作记录是否满足红队对授权范围、过程时间线、证据链、复现步骤和报告交付的要求？
7. 这些结论能否迁移到 Alvax 的“分析 → 计划 → 修改 → 审核 → 发布 → 留痕”工作流？

## 核心假设

| 假设 | 验证方式 | 当前判断 |
| --- | --- | --- |
| Issue 可以成为稳定的协作单元 | 运行递归拆解、父子层级、`blocks` 依赖和 continuation 汇总 | 初步成立，但等待与唤醒策略需要重做 |
| Agent 可以通过共享记录完成异步协作 | 观察评论 mention、固定会话、进度、广播和交付附件 | 初步成立，结构化程度仍不足 |
| 分层记忆可以缓解上下文压缩和跨会话遗忘 | 使用 Issue/Execution 级工作笔记与 Agent 级持久 Memo | 方向成立，需要防止错误、过期和敏感信息长期残留 |
| 独立验收可以减少“自报完成” | 使用固定验收 Agent、返工和人工兜底 | 方向成立，当前误拒率和证据读取问题明显 |
| 多 Agent 能减少人工协调 | 统计人工评论、Agent 唤醒和跨 Issue 广播 | 尚不能下结论，调度开销偏高 |
| 红队场景能代表复杂专业服务协作 | 执行授权目标评估和受控 C2 原型开发实验 | 能暴露问题，但不能直接证明 SEO 场景有效 |
| 运行记录可以支持成本与效率判断 | 记录 token、cost、执行次数、耗时和状态 | 未成立，当前计量数据需要校准 |

## 验证范围

### 本阶段包含

- Task、Issue、Execution、Session 四层工作模型。
- Agent 角色定义、工具、Skills、知识库和权限边界。
- Issue 递归拆解、父子层级、依赖阻塞、并行调度和原子 checkout。
- continuation 汇总、返工、取消、恢复、时间预算和人工验收兜底。
- Issue 评论、结构化 mention、固定 Agent 会话、任务广播和进度上报。
- 运行消息、事件、附件、验证结果和时间线的可观察性。
- 本地与容器执行环境，以及文件、网络、Shell 和工具调用控制。
- 红队角色协作实验和多组件工程协作实验。

### 本阶段不包含

- 不验证 Alvax 的 SEO 策略、排名或获客效果。
- 不验证 WordPress、Webflow、Search Console 或实际发布流程。
- 不把当前红队实验结果视为可直接用于生产的安全产品能力。
- 不验证市场记录中“不同模型生成内容会受到不同搜索引擎对待”的传闻；该信息仍需独立、可复现的研究。

## 为解决协同问题增加的关键机制

这些机制不是单纯增加功能，而是分别对应多 Agent 协作中已经观察到的问题。每个机制解决一个问题的同时，也会引入新的治理成本。

### 1. 任务广播：解决 Agent 之间的信息孤岛

**问题：** 多个 Agent 分别处理不同 Issues 时，关键发现、共享接口、约束变化和阻塞通常只存在于某一个 Session 中。依赖它逐个通知其他 Agent，容易延迟、遗漏或在转述中失真。

**机制：** 增加任务树级广播，作用类似群聊。Agent 可以把对兄弟 Issues 有价值的信息写入持久化广播；当前在线的 Agent 会收到通知，后加入或恢复的 Agent 也可以读取历史。广播不改变 Issue 所有权，也不能覆盖接收者的权限和目标。

**已观察效果：** 当前实验产生了 28 条跨 Issue 广播。C2 实验中，Agent 使用广播同步 API 契约、共享模型和集成状态，减少了各自按照不同接口继续实现的情况。

**新问题：**

- 广播过多会退化成噪声，增加上下文和 token 消耗；
- 不同 Agent 的广播可能互相冲突，不能把广播内容直接当成事实；
- 广播可能扩大敏感信息的传播范围；
- 需要重要性、主题、去重、引用来源和已读状态等进一步治理。

### 2. Agent 个人工作笔记：解决上下文压缩后的当前任务失忆

**问题：** 长任务会经历上下文压缩、进程恢复、工具输出截断或多轮等待。只依赖聊天历史时，Agent 容易忘记已经验证过的事实、当前阶段、下一步动作和仍未解决的阻塞。

**机制：** 通过阶段进度和 checkpoint 形成 Issue/Execution 级的个人工作笔记。Agent 在调查、设计、实现、验证等关键阶段结束后，记录“完成了什么、证据是什么、接下来做什么”；系统恢复或负责人检查时可以直接读取这些里程碑，而不是重新回放全部对话。

**已观察效果：** 当前有 300 条进度记录，覆盖 53 个 Issues。它们提升了操作者查看进度、父 Agent 检查子任务和服务恢复后续接工作的能力。

**新问题：**

- 工作笔记是 Agent 的状态陈述，不等于完成证据；
- 如果 Agent 忘记记录或记录不准确，恢复时会延续错误状态；
- 笔记过细会变成另一份冗长日志，过粗又无法支持恢复；
- 需要区分事实、假设、决定、待办和阻塞，并允许后续记录显式纠正旧结论。

### 3. Agent 持久记忆：解决跨 Session 的长期经验丢失

**问题：** 单个 Issue 的工作笔记只服务当前任务。新的 Session 启动后，Agent 仍可能忘记用户或负责人的稳定偏好、反复出现的纠正、长期工作习惯和自己经常犯的错误。

**机制：** 为每个 Agent 增加持久 Memo。它独立于具体 Issue 和 Session，Agent 可以读取或更新；新 Session 的初始上下文会注入该 Memo。设计上只保存稳定偏好、长期经验和重复教训，不保存一次性任务细节、凭据或未经证实的判断。

**已观察效果：** 已实现持久化、跨重启读取、首次 Session Prompt 注入以及 Agent 自助读写工具；现阶段主要完成了机制验证，尚未积累足够长时间的数据评价其长期收益。

**新问题：**

- 错误记忆会跨任务持续污染决策，比单次上下文错误影响更大；
- 旧偏好可能过期，且可能与新的明确要求冲突；
- 外部内容可能通过 Agent 写入持久记忆，形成长期提示注入；
- 需要来源、版本、更新时间、有效期、人工审阅、删除和敏感信息扫描。

### 4. Proof or Stop 验收：解决 Agent “自报完成”

**问题：** 执行 Agent 容易把“写完了”“命令跑过了”或一段总结当成完成，但操作者真正关心的是目标是否达成、结果是否可访问、内容是否属实、测试是否通过以及证据能否复核。

**机制：** 受 Jeffery 前几天在群里分享的 **Proof or Stop** 思路启发，把执行与验收分离：执行 Agent 必须提交面向目标的最终结果和证据；独立验收 Agent 只能根据 Objective、交付正文和附件作出通过、返工或基于证明停止的结构化决定。固定验收 Session 保留上一轮反馈，验收失败会唤醒原 Worker 返工。

**已观察效果：** 从实际试跑看，这个机制明显减少了“有总结但没有交付”“代码存在但未验证”和“子任务各自完成但整体不可用”等问题，交付质量有明显改善。

**新问题：**

- Objective 写得模糊、不可验证或包含不可控结果时，验收 Agent 没有稳定判断基准；
- 验收 Agent 看不到产物或误解证据时，会产生错误返工；
- Worker 与 Validator 可能进入反复失败的死循环，持续消耗预算；
- “Stop”必须要求目标确实不可达的证明，不能把未完成包装成不可完成；
- 当前使用最大验收次数、终局验收、不可达证明和人工兜底来打断循环，但还需要目标版本、失败分类和验收校准集。

### 5. Issue 与资源预算：解决任务树和执行成本失控

**问题：** Agent 可以继续拆分、返工、恢复和唤醒。如果没有边界，一个目标可能产生无限子 Issues、过深层级、长期运行、大量 token 或不可接受的模型费用。

**机制：**

- **Issue 预算：** 限制最大拆解深度、单次创建子 Issue 数量和每个父 Issue 的直属子项数量，避免任务树爆炸。
- **时间预算：** 限制根 Issue 当前 Execution 的运行时间。
- **Token 预算：** 限制根 Issue 当前 Execution 的 token 使用量。
- **价格预算：** 根据模型价格快照限制根 Issue 当前 Execution 的成本。
- 任一资源预算耗尽后，系统要求 Agent 总结已有成果并停止继续追逐原目标。

**已观察效果：** 时间预算已经实际触发过停止，证明系统能够阻止任务无限运行，同时保留阶段成果和停止原因。

**新问题：**

- 预算设得太低会在接近完成时强制停止，太高则失去保护意义；
- 当前资源预算按根 Issue 的“当前一次 Execution”计算，新 Execution 会重置，无法限制整个任务树的累计消耗；
- 子 Issues、验收、心跳和协调开销尚未统一计入任务总预算；
- token 和价格计量当前不可靠，预算判断可能失真；
- 后续需要 task-tree 总预算、分项预算、80% 预警、申请追加预算和降级策略，而不是只有继续或停止。

### 6. 可观测性：解决 Agent 黑盒执行和无法干预

**问题：** 当 Agent 长时间运行、卡住、重复调用工具或给出异常结果时，如果只能等待最终回答，操作者无法判断它是在正常工作、等待依赖、偏离目标还是已经失控，也无法进行有效复盘。

**机制：** 增加 Session 消息、工具调用与参数摘要、当前工具、checkpoint、阶段进度、事件、token/cost、附件、依赖图、任务时间线、心跳状态、中断工具和人工验收入口。

**已观察效果：** 当前已经能够从 Task 下钻到 Issue、Execution 和 Session，定位等待、返工、验证失败、工具错误和 Agent 之间的信息流；本轮发现 heartbeat 占 66.5% 和验收证据路径问题，本身就是可观测性带来的直接价值。

**新问题：**

- 记录越完整，敏感信息、存储和合规风险越高；
- 事件太多会让真正异常被噪声淹没；
- token/cost 等指标如果口径错误，会产生“看起来精确”的错误判断；
- 需要面向操作者的异常摘要、关键路径、等待原因和协调开销，而不只是把所有底层事件展示出来。

## 实验场景

### 场景 A：授权红队任务

由红队负责人拆分信息收集、漏洞验证和报告编写等子 Issues，观察：

- 目标与范围能否被子 Agent 正确继承；
- 发现能否及时广播给其他执行 Agent；
- 每条结论是否附带可复核证据；
- 负责人能否基于子任务记录完成最终汇总；
- 高风险工具行为是否可被中断、审批和审计。

### 场景 B：受控 C2 原型开发

将后端、Agent、CLI、前端和集成测试分配给不同 Agent，观察：

- 共享接口变化是否能及时同步；
- Issue 依赖能否避免错误的执行顺序；
- 多 Agent 是否会在共享工作区相互覆盖；
- 验收 Agent 能否读取构建、测试和端到端证据；
- 子任务完成后父任务能否稳定收敛。

### 场景 C：Alvax 影子试点（待执行）

在隔离的单一建站系统中模拟“3 个页面修改 + 2 个内容机会 + 少量技术修复”，只验证流程正确性、证据、审批、回滚和人工耗时，不承诺排名或流量变化。

## 阶段结论

### 已得到支持的结论

1. **Issue 模型可以承载多 Agent 工作。** 父子层级用于拆分目标，`blocks` 用于表达执行顺序，Execution 保留每次尝试，Session 保留 Agent 上下文，这四类对象有必要分开。
2. **异步协作必须写入公共事实源。** 评论、广播、进度和附件能让接口变化与关键发现脱离单个 Agent 的上下文窗口；C2 实验中已经出现通过广播对齐 API 契约的记录。
3. **“完成”必须与“验收通过”分离。** 执行 Agent 提交结果后由独立会话读取证据并决定通过、返工或人工接管，比单纯依赖 Agent 自报完成更接近真实交付。
4. **可观察和可干预是产品能力，不是调试附属品。** Session、事件、当前工具、时间线、中断和手工验收，是用户建立信任的基础，也直接对应 Alvax 市场记录中的“可核对的变更”。
5. **专业角色有价值，但角色越多不一定越好。** 负责人、执行者和验收者的职责边界较清晰；继续增加角色会放大通信和调度成本。
6. **记忆必须分层。** 当前任务事实应进入 Issue/Execution 工作笔记，稳定偏好和长期教训才进入 Agent 持久记忆；两者都不能替代可验证的交付证据。

### 已暴露的主要瓶颈

1. **心跳唤醒形成调度风暴。** 331 次执行中有 220 次 heartbeat，约占 66.5%。部分等待 Issue 单独产生 20–40 次心跳。等待本身正在消耗大量 Agent 执行，应改成事件驱动，心跳只负责超时兜底。
2. **验收证据链不稳定。** 当前 39 次验收仅 15 次通过。容器路径与宿主机附件路径不一致时，产物实际存在，但验收 Agent 无法读取，导致多轮返工和误拒。验收必须使用统一、不可变、可寻址的 artifact manifest。
3. **token 与成本统计不可用于决策。** 数据库累计 token 约 22.6 亿，但 cost 全为 0。该数字很可能重复累计了恢复会话或心跳的 session 快照；在修正计量前，无法证明多 Agent 比单 Agent 更省成本。
4. **共享工作区会造成隐式耦合。** 不同 Agent 会读取或修改同一组文件，接口改变、生成物路径和未提交文件都可能相互影响。Issue 依赖图无法完全解决文件级冲突，需要工作区隔离、明确所有权和合并机制。
5. **记录中可能残留敏感信息。** 红队执行的原始消息和结果可能包含会话凭据、目标细节或利用证据。当前系统强调“完整留痕”，但缺少自动脱敏、密级、保留期限和导出审查，不能直接用于生产。
6. **取消率不能表达任务质量。** 61 个 Issues 中 46 个被取消，多数与重跑、预算、父任务终止或架构迭代有关。需要区分用户取消、被上游取消、试验废弃、超时和系统故障，才能形成可解释指标。
7. **权限与授权需要成为领域对象。** 现有工具权限和工作区边界可以控制“怎么做”，但红队习惯还要求先明确“允许对谁、在什么时间、以什么手段做”。范围、授权、停止条件和证据敏感级别应被系统强制执行。
8. **记忆会把错误从短期问题放大为长期问题。** 工作笔记可能记录错误进度，持久 Memo 可能保存过期或被注入的信息。需要来源、有效期、冲突优先级、人工审阅和删除机制。

## 对 Alvax 的直接启示

1. 首期不要追求大量 Agent，建议只保留 Planner、Executor、Reviewer 三个责任面；发布动作继续由用户批准。
2. 每个页面修改都应形成结构化变更包：原始内容、建议、理由、diff、来源、风险、验证结果和回滚信息。
3. 调度器应以状态变化和依赖完成事件为主，避免用模型心跳轮询普通等待状态。
4. 审核必须读取同一份可寻址产物，不能让执行 Agent 与审核 Agent 分别解释不同工作区里的文件。
5. 首期指标应是批准率、修改轮数、人工分钟数、单次交付成本、验收误拒率和发布后故障率，不是排名或流量。
6. 只支持一种建站系统不仅是市场范围控制，也是降低 Agent 工具、权限和验证矩阵复杂度的架构要求。
7. AI 内容必须经过事实、品牌和发布三类检查；关于搜索引擎是否区别对待特定模型内容的说法，在完成独立验证前不得进入产品承诺。
