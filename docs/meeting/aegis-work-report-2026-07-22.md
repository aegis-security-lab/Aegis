# Aegis 工作记录与 Alvax 多 Agent 架构验证汇报

> 适用场景：项目例会或阶段评审，建议讲述时间 8–10 分钟。  
> 汇报日期：2026-07-22

## 一句话定位

**Aegis 不是另一个业务产品，而是我为 Alvax 搭建的多 Agent 架构试验场：先用我熟悉、复杂度高、强调证据链的红队场景把问题跑出来，再把可复用的结论带回 Alvax。**

## 30 秒开场稿

这段时间我做了一个叫 Aegis 的项目。它不是为了替代公司的 Alvax，也不是准备单独做一个网安产品。我做它的核心目的，是提前验证基于 Issues 的多 Agent 协同是否真的可行。

Alvax 的市场调研里有一个很重要的判断：客户缺少的不是更多报告，而是可信、可核对、经过批准、能够追溯的实际变更。多 Agent 如果只是能自动生成内容，但任务怎么拆、谁改了什么、证据在哪里、为什么返工、用户什么时候批准都说不清楚，就无法解决这个信任问题。

所以我选择自己熟悉的红队和安全研发场景做压力测试。这个领域过程不确定、角色多、依赖多、证据要求高，也容易出现高风险操作，比较适合提前暴露架构问题。

## 我完成了什么

从 7 月 16 日到 7 月 22 日，我把 Aegis 从一个前端骨架推进成了真实 Agent 驱动的本地多 Agent 控制台。当前代码有 16 个提交，工作区约 46,700 行代码，包含 42 个 Go 测试文件和约 208 个测试函数。

主要完成了六组能力：

1. **工作模型**：把用户目标定义成顶层 Task，把拆分后的工作定义成 Issues；每次尝试保留独立 Execution，每个 Agent 的运行上下文保留为 Session。
2. **协同调度**：支持递归拆分、父子层级、`blocks` 依赖、并行执行、原子 checkout、子任务结束后的父任务汇总。
3. **Agent 协作与记忆**：支持 Issue 评论、结构化 mention、固定会话续接、跨 Issue 广播、个人工作笔记、跨 Session 持久记忆和附件交付。
4. **质量控制**：支持独立验收 Agent、返工、人工复核、取消、恢复、时间预算和停止工具调用。
5. **可观察性**：可以查看消息、事件、当前工具、执行进度、token、附件、验证结果和完整时间线。
6. **执行边界**：支持本地或容器工作区，并控制网络、Shell、文件写入、工具和审批策略。

## 我重点增加的六类机制

这些机制不是为了把后台做得更复杂，而是分别解决我在多 Agent 实际运行中遇到的问题。

### 1. 广播机制：解决信息孤岛

多个 Agent 同时工作时，一个 Agent 发现的接口变化、关键证据或阻塞，默认不会自动进入其他 Agent 的上下文。我增加了任务树级广播，作用类似群聊：当前在线的 Agent 能收到，后加入或恢复的 Agent也能读取历史。

现在数据库里有 28 条跨 Issue 广播。C2 实验中，它实际被用于同步 API 契约、共享模型和集成状态。

这个机制有效，但要防止群聊退化成噪声。广播必须只发会影响其他 Issues 的信息，还要考虑冲突、去重、可信度和敏感信息传播。

### 2. Agent 个人工作笔记：解决上下文压缩后的失忆

长任务会发生上下文压缩、工具输出截断、进程恢复和长时间等待。Agent 如果只依赖聊天记录，很容易忘记已经做过什么、哪些事实已经验证、下一步是什么。

我把阶段进度和 checkpoint 作为 Issue/Execution 级的个人工作笔记。Agent 在完成调查、设计、实现或验证阶段后，记录完成内容、证据和下一步。目前有 300 条记录，覆盖 53 个 Issues。

它能帮助恢复和上级 Agent 检查进度，但笔记只是状态陈述，不是 Proof。后续还要把事实、假设、决定、待办和阻塞分开，并允许明确纠正旧记录。

### 3. Agent 持久记忆：解决跨 Session 遗忘

个人工作笔记服务当前任务，持久记忆服务 Agent 自身。我增加了 Agent 级 Memo，用来保存稳定的用户偏好、负责人的长期要求、重复纠正和 Agent 经常犯的错误。它会跨 Session、跨服务重启保存，并在新 Session 初始上下文中注入。

这类记忆不能保存一次性任务细节、凭据和未经验证的结论。否则一次错误可能污染后续所有任务。下一步需要补来源、版本、有效期、人工审阅、删除和提示注入防护。

### 4. Proof or Stop 验收：解决“自报完成”

这个机制受到 Jeffery 前几天在群里分享的 **Proof or Stop** 思路启发。核心不是让执行 Agent 再写一段更好看的总结，而是要求它提交面向目标的结果和可复核证据，再由独立验收 Agent 决定通过、返工，或者在有充分证明时停止。

从实际试跑看，效果明显变好。以前容易出现“代码写了但没有测试”“各个子任务都说完成但整体跑不起来”“只有总结没有交付物”；加入验收后，这些问题更容易被拦下来。

它也带来了两个核心问题：

1. **验收什么。** Objective 如果模糊、不可验证或包含排名、流量这类不可控结果，验收 Agent 就没有稳定标准。
2. **一直验收失败怎么办。** Worker 与 Validator 可能反复返工，形成成本死循环。

我目前增加了最大验收次数、固定验收 Session、最终验收轮次、不可达证明、人工兜底和人工改判。后续还需要目标版本、验收失败分类和一套校准样本，确保 Validator 不会过严或过松。

### 5. Issue、时间、Token 和价格预算：解决无限拆分与成本失控

我把预算分成两层：

- Issue 预算限制最大拆解深度、单次子 Issue 数量和直属子项数量，防止任务树无限膨胀；
- 时间、Token 和价格预算限制执行资源，达到阈值后要求 Agent 总结已有成果并停止继续追逐原目标。

时间预算已经在实验中实际阻止过长时间运行。不过当前资源预算只统计根 Issue 的当前一次 Execution，新 Execution 会重新计数，子 Issues、验收、心跳和协调成本也没有全部纳入，所以还不是完整的任务总预算。

下一步应该做 task-tree 累计预算、80% 预警、分角色额度、追加预算申请和降级策略，而不是预算到了就只有强制停止。

### 6. 可观测性：解决 Agent 黑盒执行

如果只能看到 Agent 的最终回复，就无法判断它正在正常工作、等待依赖、重复调用工具还是已经偏离目标。我增加了 Session 消息、工具调用、当前工具、checkpoint、阶段进度、事件、附件、token/cost、依赖图、任务时间线、工具中断和人工验收入口。

这次能发现 331 次执行中有 220 次 heartbeat、验收 Agent 因路径问题读不到证据，靠的就是这些记录。

可观测性也不是记录越多越好。记录太多会产生噪声、存储和敏感信息风险；指标口径错误还会制造“看起来很精确”的错误结论。后续要重点展示异常、等待原因、关键路径和协调开销。

## 这六类机制形成的整体闭环

可以把它们理解为一个协作闭环：

1. Issue 和资源预算先限定系统可以做多少；
2. Agent 执行时用个人工作笔记保存当前状态；
3. 需要影响其他 Agent 的信息通过广播共享；
4. 稳定、可复用的经验才进入持久记忆；
5. 最终结果必须经过 Proof or Stop 验收；
6. 全过程由可观测性记录和支持人工干预。

这里最重要的边界是：**工作笔记不是证据，广播不是事实，持久记忆不是最高指令，执行完成也不是验收通过。**

## 我怎么验证

我没有只做静态功能，而是跑了两类真实实验。

第一类是**授权红队任务**。由红队负责人拆解信息收集、漏洞验证和报告等子任务，观察范围能否继承、关键发现能否共享、证据能否复核，以及负责人最后能否完成汇总。

第二类是**受控 C2 原型开发**。把后端、Agent、CLI、前端和集成验证分配给不同 Agent，专门观察接口同步、依赖顺序、共享工作区冲突、端到端验收和父任务收敛。

当前本地运行数据主要覆盖 7 月 20 日到 7 月 22 日：

| 指标 | 当前记录 |
| --- | ---: |
| 顶层任务 | 16 |
| 可见 Issues | 61 |
| Agent Executions | 331 |
| 自动拆解 | 10 次，平均 4.5 个子 Issues |
| Issue 依赖 | 90 条 |
| 进度记录 | 300 条，覆盖 53 个 Issues |
| Issue 评论 | 327 条，其中 301 条来自 Agent |
| 跨 Issue 广播 | 28 条 |
| 验收 | 39 次，15 通过、23 失败、1 跳过 |
| 附件 | 51 个，覆盖 21 个 Issues |

这批数字的意义是系统确实跑过了多轮协同，不代表已经达到生产成功率。46 个 Issues 被取消，其中很多是重跑、父任务终止、预算到期和架构调整产生的实验记录，不能直接解释成任务失败。

## 已经验证出的价值

### 1. Issue 可以作为多 Agent 的协作单元

父子关系负责表达“目标怎么拆”，依赖关系负责表达“工作按什么顺序做”。两者分开以后，可以让不同 Agent 并行，又不会把所有协调逻辑写进 Prompt。

### 2. 公共记录比共享对话更重要

Agent 之间真正有用的协作信息，主要是接口约定、关键发现、证据、风险和阻塞。把它们写到 Issue 评论、广播和附件中，比让所有 Agent 共享一段越来越长的聊天上下文更稳定。

### 3. 执行完成和验收通过必须分开

Agent 说“我完成了”不能直接代表任务完成。Aegis 使用独立验收会话读取目标和证据，再决定通过、返工或交给人工，这个方向符合专业服务交付，也符合 Alvax 需要的用户信任模型。

### 4. 用户需要看到并控制过程

Session、时间线、diff/附件、当前工具、中断和人工验收不是后台调试功能，而是产品的一部分。它们对应了市场调研中的核心需求：用户要知道改了什么、为什么改、能不能批准，以及出问题后怎么追溯。

## 提前踩到的坑

### 1. Agent 在“等待”上浪费了大量执行

331 次执行中有 220 次是 heartbeat，约占 66.5%。有些等待中的 Issue 被唤醒了 20–40 次，只是重复确认依赖尚未结束。

这说明普通等待不应该启动模型。后续应改为事件驱动：依赖状态变化时再唤醒 Agent，心跳只负责低频超时兜底。

### 2. 验收失败不一定代表工作失败

39 次验收只有 15 次通过。实验中已经遇到文件存在于容器工作区，但宿主机附件路径不可读，导致验收 Agent 看不到证据、不断要求返工。

这说明执行和验收必须读取同一个不可变交付物，后续需要统一 artifact manifest、路径映射、哈希和权限协议。

### 3. 当前成本数据不可信

数据库累计 token 约 22.6 亿，但 cost 全部为 0。较大概率是恢复会话和 heartbeat 重复记录了累计 usage，而不是每次 execution 的增量。

在修正计量前，不能声称多 Agent 更省钱。以后必须把真正执行工作的消耗、协调消耗、验收消耗和空转消耗分开。

### 4. 共享工作区会造成隐形冲突

即使 Issues 没有依赖冲突，不同 Agent 仍可能修改相同文件、改变共享接口或把产物放到彼此不可见的位置。后续需要明确文件所有权、隔离工作区和合并规则。

### 5. 完整留痕也会带来安全风险

红队原始记录里可能出现目标信息、临时凭据和利用证据。当前系统能完整记录，但还缺自动脱敏、密级、保留期限和导出审查。

这对 Alvax 同样重要，因为 Search Console、CMS 和客户营销数据也属于敏感信息。审计与最小暴露必须同时设计。

### 6. 角色太多会放大通信成本

领域角色有帮助，但角色越多，handoff、重复解释和等待就越多。对 Alvax 首期更合理的是三个责任面：Planner、Executor、Reviewer；发布继续由用户批准。

## 是否符合我的红队工作习惯

我的阶段判断是“部分符合，已经接近工作台，但还不能当作生产级红队协同系统”。

| 红队习惯 | 当前符合度 | 判断 |
| --- | --- | --- |
| 任务按阶段和角色拆分 | 较高 | 父子 Issues、依赖和负责人汇总比较自然 |
| 关键发现及时同步 | 较高 | 广播和固定 Issue 记录有效，避免只存在某个 Agent 对话里 |
| 原始证据可复核 | 中等 | 有附件、消息和时间线，但跨环境证据读取仍不稳定 |
| 失败后能复盘与续接 | 中等偏高 | Execution 与 Session 分离，返工和恢复有记录 |
| 授权范围和停止条件 | 偏低 | 有工具权限和时间预算，但缺少一等公民的 ROE/授权对象 |
| 敏感信息管理 | 偏低 | 留痕完整，但自动脱敏、密级和导出控制尚未完成 |
| 报告可直接交付 | 中等 | 已有 findings、评论和附件，仍需要统一证据与报告模板 |

最符合红队习惯的是“分工、证据、时间线和复核”；最不符合的是“授权范围强制执行、证据链稳定性和敏感信息治理”。

## 与 Alvax 市场记录的对应关系

| 市场记录中的要求 | Aegis 得到的架构启示 |
| --- | --- |
| 客户不想再看一份看不懂的报告 | 每个建议必须落成可检查的 Issue 和变更包 |
| 用户关心可信、可核对的变更 | 保存 before/after、理由、来源、验证和回滚信息 |
| 用户批准后再发布 | 发布作为单独的人工审批动作，不能由内容 Agent 默认完成 |
| 两周只验收执行正确，不承诺排名 | 验收流程、事实、页面可用性和追踪基线，不验收不可控结果 |
| 首期只支持一种建站系统 | 减少工具、权限、验证和回滚矩阵，先把流程跑稳 |
| AI 内容可能伤害品牌 | 作者与 Reviewer 分离，并增加事实、品牌和发布三道检查 |
| 服务 + 软件，而非纯自助 | Agent 自动执行，人工负责范围、批准、例外和最终责任 |

市场记录里关于 Gemini 内容可能受到较宽松对待的说法目前只是传闻。这个判断没有被 Aegis 验证，也不应进入产品承诺；我们应以内容质量、事实和用户价值为审核标准。

## 我建议 Alvax 下一步怎么做

不要直接把当前多角色系统搬进 Alvax。下一步先做一次范围很小的影子试点：

- 只选 WordPress 或 Webflow 一种系统；
- 只使用 Planner、Executor、Reviewer 三个 Agent 责任面；
- 在沙箱网站执行 3 个页面修改、2 个内容机会和少量技术修复；
- 每个变更都保留 before/after、理由、来源、验证和回滚方式；
- 所有发布动作都由用户批准；
- 记录批准率、修改轮数、人工分钟数、单次成本、验收误拒率和故障率；
- 同时跑一个单 Agent 对照组，判断多 Agent 增加的质量是否值得额外成本。

在试点前优先解决四个 P0 问题：事件驱动调度、统一证据协议、敏感信息治理、可靠的 token/cost 计量。

## 30 秒收尾稿

这阶段 Aegis 最重要的产出不是“已经做出了一个完整产品”，而是用真实任务证明了 Issue 驱动的多 Agent 协同能够工作，同时提前暴露了等待空转、验收证据、共享工作区、成本统计和敏感信息治理这些问题。

这些问题如果等到 Alvax 接入真实客户网站、Search Console 和 CMS 后再发现，修复成本会高很多。现在更合适的做法是把 Aegis 得到的约束带回 Alvax，用更少的角色、更窄的系统范围和更明确的证据与审批机制完成下一轮试点。

## 被追问时的简短回答

### “为什么不用 SEO 场景直接验证？”

红队场景是我熟悉的高复杂度压力测试，可以更快识别协作和审计问题；但它不能替代 SEO 验证，所以后续仍需要单一 CMS 的 Alvax 影子试点。

### “61 个 Issues 里取消了 46 个，是不是系统失败率很高？”

不能这样解释。当前取消混合了主动重跑、父任务终止、预算到期、架构调整和系统问题。它本身反而说明我们缺少标准化 reason code；在重新分类前不能把取消率当成质量指标。

### “多 Agent 到底比单 Agent 好在哪里？”

目前能确认的是职责分离、独立验收和公共证据更清晰；还不能确认成本更低。需要在 Alvax 影子试点里与单 Agent 对照，并修正 token/cost 统计后再下结论。

### “这个项目现在能投入生产吗？”

不能。它已经完成阶段性架构验证，但事件调度、证据传递、敏感信息治理、权限授权和成本计量仍需要达到生产标准。
