# 建议开发路线

## 阶段 0：现在——研究基座

已经具备：安全 Electron 外壳、Agent / Run 契约、本地持久化、模拟编排器、事件流和打包链路。

研究重点：

- 用户真正希望多个 Agent 帮他完成什么结果？
- 用户想看协同过程，还是只想控制关键检查点？
- Agent 是团队长期资产，还是任务中的临时角色？
- 需要人类批准的节点在哪里？

## 阶段 1：第一个真实纵切

只选择一个高价值场景，例如“调研 → 反方审查 → 产品建议”，端到端接通：

1. 系统钥匙串 `CredentialVault`；
2. 一个 OpenAI-compatible `AgentRuntime`；
3. 流式文本事件和取消；
4. 一种受控工具（例如只读资料检索）；
5. 输入、输出、成本、耗时和错误的可观测性；
6. 用 10–20 个固定任务做回归评估。

这一阶段不建议同时接多家 provider，也不建议做通用工作流画布。

## 阶段 2：可复用协同

- 按已验证需求实现 supervisor / round-robin / pipeline 中的一种；
- 将工具调用纳入权限策略和人工确认；
- Run event store 升级为 SQLite；
- 支持任务恢复、重试、checkpoint 和 artifact；
- 建立 prompt / AgentDefinition 版本和评估集关联。

## 阶段 3：团队产品化

- 工作区、团队身份和细粒度权限；
- 远端同步与离线冲突策略；
- 企业审计、数据保留、导出和删除；
- 签名更新、灰度、崩溃恢复和发布流水线；
- 将长任务或不可信工具隔离到 utility process / sidecar。

## 架构门槛

在满足触发条件前不提前增加复杂度：

| 能力 | 触发条件 |
|---|---|
| SQLite | 查询、回放、并发或迁移需求出现 |
| 后端队列 | 任务必须跨设备或应用退出后继续 |
| 图编排 DSL | 用户已验证需要非线性流程且复用频繁 |
| 多窗口 | 已出现明确的独立工作上下文 |
| 多 provider | 单 provider 已跑通并有成本/可靠性理由 |
| 插件系统 | 至少有 3 个外部团队需要独立扩展 |

## 发布前硬门槛

- 所有 CI 检查和平台 package / make 通过；
- 0 个未经评估的 production dependency 高危漏洞；
- Apple / Windows 签名和自动更新签名验证；
- Secret redaction、最小日志、SBOM 与第三方许可清单；
- IPC、导航、协议路径穿越和工具权限安全测试；
- 崩溃恢复、数据迁移回滚和卸载数据策略。
